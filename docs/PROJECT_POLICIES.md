# IndustrialRust1710 — プロジェクトポリシー

最終更新: 2026-10-27

この文書は、RustネイティブのMinecraft Java Edition 1.7.10（Protocol 5）サーバーを、安全に並行開発するための共通基準です。人間・AIエージェント・定期実装タスクを含む、すべての変更に適用します。

## 1. 基本原則

1. **安全とデータ保全を最優先**：ワールド、プレイヤー、アイテム、セーブデータを破損させる可能性がある変更は、バックアップ・復旧手順・テストなしに採用しません。
2. **本体・実行時はRustのみ**：Minecraftサーバー、管理GUI、本番運用ツール、常駐プロセス、通信・保存・ロジックの実装にはRustを使います。Pythonは独立した検証、監査、テスト、ベンチマーク専用です。シェル/PowerShellは薄いビルド・起動ラッパーのみ。詳細と既存の移行例外は[AGENTS.md](../AGENTS.md)を優先して参照します。
3. **正しさを互換性より先に偽装しない**：自動テストが通っても、無改造1.7.10クライアントで確認していない機能を「実機互換確認済」と記載しません。
4. **小さく検証可能な変更**：独立した論点は別PRに分離し、再現手順・期待結果・影響範囲を明示します。
5. **証拠に基づく完了宣言**：実装済・Rustテスト済・CI通過・Windows実機確認済・バニラ1.7.10実機確認済を区別します。未実施は「未実施」と書きます。

## 2. 優先順位・スコープ

- 現行の対象は**RustネイティブのバニラMinecraft Java 1.7.10 / Protocol 5**です。Forge/FML/Modの完全互換は現時点の完了条件には含めません。最新スコープは[要件定義](01_要件定義.md)と[README](../README.md)を参照します。
- **P0**：接続不能・クラッシュ・セーブ破損・権限逸脱・アイテム重複/消失など。再現テスト、最小修正、後方互換を優先。
- **P1**：主要なゲーム進行・操作の不一致、顕著な性能退行など。
- **P2**：機能拡張・軽微な品質改善・文書化など。
- 競合する要求はIssue/PRに記録し、既存の実装・最新mainを確認してから判断します。未確定仕様を「公式1.7.10互換」として既成事実化しません。

## Rust CIの運用変更（2026-10-27）

**GitHub Actions上のRust CIは今後起動・再実行しません。** push/PRの自動起動は停止しました。Rustコードの品質確認は開発PC等のローカル環境で必要に応じて実施し、実行できない場合は未実施と記録します。保護ルールで停止済のRustチェックが必須になっていれば、管理者がrequired check設定を解除するまでマージを保留します。テスト未実施を成功とは報告しません。具体的な例外とゲートは[詳細ポリシー](POLICY_RULES.md)に従います。

## 3. コード品質・テスト

Rustの変更では、可能な環境で以下を実行し、PRに成功/失敗/未実施の結果を記録します。

```bash
cargo fmt --all -- --check
cargo test --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
cargo build --release -p vanilla-server -p legacy-status-server
```

- 関連するRust単体テスト・TCP結合テスト・回帰テストを追加します。Pythonはあくまで外部からの検証ドライバーとして利用できます。
- Protocol 5、座標、チャンク境界、負座標、移動、コンテナ・NBT、再接続、異常終了後の再起動に関わる変更は、該当する境界条件を試験します。
- Windows起動や管理GUIの変更は、Windows実機で検証したかを明示します。Minecraft実機検証が必要な変更は、クライアント版と検証手順を記録します。
- CIの緑表示のみで未実施の実機試験を置き換えません。テストを省略・無効化した場合は理由と代替検証をPRで明記します。

## 4. 保存・互換性・回復可能性

- 既存ワールドやユーザーデータの直接上書き・一括削除・未検証の自動移行は禁止します。新フォーマットへの移行は別の作業コピーで検証します。
- 保存経路を変更したら、正常保存、再読み込み、クラッシュ時の復旧、部分書き込み、複数ファイルの整合性、重複処理を確認します。
- 未知NBT/未対応データを黙って捨てず、必要なら安全に拒否します。
- テストに実アカウント情報、秘密鍵、個人のワールドデータ、Minecraft/Mod配布物をコミットしません。

## 5. セキュリティ

- クライアントから受け取るパケット、座標、インベントリ、コマンド、NBT等はすべて未信頼入力として扱います。サイズ・個数・範囲・レートの上限と、サーバー権威による状態確認を実装します。
- 名前ベースのホワイトリストは本人確認ではありません。認証・権限・外部公開について、実証済でない安全性を保証しません。
- デフォルトは開発用のローカル待受とし、公開運用を前提にした変更は認証・権限・DoS耐性・ログの取り扱いを別途レビューします。
- 脆弱性の詳細は公開Issueへ書き込まず、[SECURITY.md](../SECURITY.md)の手順を利用してください。

## 6. PR・マージ・ブランチ運用

- 1PRにつき原則1つの検証可能な変更。関連Issue、変更点、テスト、未確認事項、データ移行/ロールバック方針を記載します。
- **既存のopen PRとmainの変更を確認し、重複実装・巨大な一括上書きを避けます。** CI失敗、未解決の重大なレビュー指摘、明らかな保存破壊リスクがあればマージしません。
- ドキュメントのみのPRでもリンク切れ・既存ルールとの矛盾を確認します。CI・レビュー・権限制御はGitHubの実際の設定に従います。この文書はbranch protectionや必須承認人数が設定済であることを意味しません。
- マージ済のブランチ削除はコミット取り込み、open PRとの関係、ほかの作業者の利用状況を確認してから行います。強制pushや作業中ブランチの一括削除をしません。

## 7. AIエージェント・並列担当

- A/B/C等の担当は着手前にmain、Issue、open/draft PR、関連CIと担当領域を確認します。
- 担当範囲外への大規模変更はIssue/PRで意図と衝突リスクを説明し、重複を調整してから着手します。
- 実装したコード、検証の証拠、未実施試験、依存PR、次の課題を追跡可能にします。**AIが「修正済」「マージ済」「検証済」と報告できるのは、その操作・結果を確認した場合だけ**です。
- 重大なリスクがある場合は自動的に安全な停止/保留を選び、実データの破壊や権限緩和で成功を装いません。

## 8. 改定方法・関連文書

このポリシーの変更も通常のPRとして提案し、影響を説明します。矛盾を発見したら独断で解釈せずIssueで明示します。具体的な実装言語ルールは[AGENTS.md](../AGENTS.md)、参加方法は[CONTRIBUTING.md](../CONTRIBUTING.md)、脆弱性報告は[SECURITY.md](../SECURITY.md)、技術的なスコープ・受入条件は[要件定義](01_要件定義.md)を参照してください。
