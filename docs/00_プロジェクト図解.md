## 1. Cargo workspaceと各バイナリ

`Cargo.toml` に列挙された6パッケージを中心にした配置です。**矢印は役割・データの流れ**であり、すべてが直接リンクされたcrate依存であることを意味しません。

```mermaid
flowchart TB
    Client["Minecraft Java 1.7.10<br/>バニラクライアント"]
    subgraph Servers["ゲーム・通信サーバー"]
        Vanilla["apps/vanilla-server<br/>Login / Play / World / 保存"]
        Status["apps/legacy-status-server<br/>Status / Ping 専用"]
    end
    Protocol["crates/legacy-protocol<br/>Protocol 5 フレーム処理"]
    subgraph Other["独立した研究・補助ツール"]
        Analyzer["crates/mod-analyzer<br/>JAR / Modpack 静的解析"]
        Bench["apps/industrial-bench<br/>合成ベンチマーク"]
        Core["crates/industrial-core<br/>Tick / 産業ネットワーク計算"]
    end
    Saves[("独自ワールド IRW<br/>プレイヤー / コンテナ等のデータ")]
    ModJar["外部のMod JAR"]
    Client -->|"TCP / Protocol 5"| Vanilla
    Client -.->|"サーバー一覧への問い合わせ"| Status
    Vanilla --> Protocol
    Status --> Protocol
    Vanilla --> Saves
    Analyzer -->|"読み取り専用"| ModJar
    Bench --> Core
```

- `vanilla-server` はRustネイティブのゲーム本体。`main.rs` と `world.rs`、`mobs.rs`、`inventory.rs` などのモジュールに処理が分かれています。
- `legacy-status-server` はStatus専用の**別バイナリ**です。通常のゲーム参加には `vanilla-server` を使用します。
- `mod-analyzer` は静的解析用で、**Forge/FML Modの実行環境ではありません**。
- `industrial-core` と `industrial-bench` はゲーム本体とは別の計算・計測経路です。

## 2. Protocol 5の接続フロー

StatusとLoginは別の要求経路です。`--online-mode` は追加の本人確認経路を使います。次は**概念的なフロー**で、エラー応答やパケット送信の細かい順番は省略しています。

```mermaid
sequenceDiagram
    participant Client as Java 1.7.10 クライアント
    participant Server as vanilla-server
    participant Auth as online_auth / 参加制御
    participant World as World / Multiplayer
    Client->>Server: TCP接続とHandshake (Protocol 5)
    alt Status照会
        Client->>Server: Status Request / Ping
        Server-->>Client: Status / Pong
    else Login
        Client->>Server: Login Start
        opt online-mode が有効
            Server->>Auth: 暗号鍵交換・セッション照合
            Auth-->>Server: 検証結果
        end
        Server->>Auth: 設定と参加条件の確認
        alt 拒否
            Server-->>Client: Disconnect
        else 許可
            Server->>World: セッション登録・初期状態取得
            Server-->>Client: Login成功・初期チャンク等
            loop Play中
                Client->>Server: 移動・操作・チャット
                Server->>World: サーバー側で検証し更新
                World-->>Server: 状態変化・配信イベント
                Server-->>Client: Chunk / Entity / Inventory等
            end
            Server->>World: 切断時の登録解除・保存処理
        end
    end
```

**注意:** オンライン本人確認と、ホワイトリストによる許可判定は別です。設定と実装内容を確認せずサーバーをインターネット公開しないでください。

参照: `apps/vanilla-server/src/main.rs`、`online_auth.rs`、`whitelist.rs`、`multiplayer.rs`、`crates/legacy-protocol/`。

## 3. 20TPSのゲーム処理

Tickと接続セッションは同一処理ではありません。更新の責務を確認するための図で、実際のワーカースレッド数・ロック順序を規定するものではありません。

```mermaid
flowchart TD
    Clock["Clock / 20Hz"]
    Input["プレイヤー入力<br/>Protocol 5受信"]
    Validate{"サーバー側の検証"}
    Logic["World・Mob・物理・装置・生存処理"]
    Session["Multiplayer Hub<br/>参加者・有界送信キュー"]
    Snapshot["状態更新と必要な保存"]
    Network["見える範囲のChunk / Entity等を送信"]
    Reject["拒否・必要なら再同期"]
    Clock --> Logic
    Input --> Validate
    Validate -->|"正常"| Logic
    Validate -->|"不正"| Reject
    Logic --> Snapshot
    Logic --> Session
    Session --> Network
```

- `world.rs` の下位モジュール: `world/devices.rs`、`world/ecology.rs`、`world/lighting.rs`、`world/special.rs`。
- その他の主な処理: `mobs.rs`、`physics.rs`、`crafting.rs`、`furnaces.rs`、`hoppers.rs`、`minecarts.rs`。
- `multiplayer.rs` はプレイヤーを保持し、容量超過時に不整合なイベントを黙って欠落させない方針の有界キューを使います。
- **20TPSの時計が存在することは、すべての負荷条件で20TPSを維持できる証明ではありません。**

## 4. 保存・復旧と安全境界

現状のライブ処理は独自IRW形式を使用します。プレイヤー・コンテナ等の状態には別ファイルもあり、**すべての保存操作がひとつの原子トランザクションになったわけではありません**。

```mermaid
flowchart LR
    Runtime["vanilla-server<br/>ライブ状態"]
    World[("IRW1〜IRW4<br/>独自ワールド")]
    Player[("プレイヤー状態<br/>NBT / JSON等")]
    Container[("装置・アイテム等<br/>独立JSON")]
    Journal["redo journal<br/>対象を限定した複数ファイル更新"]
    Replay["起動時のjournal検証・再生"]
    Export["Anvil export / import<br/>別経路のオフライン処理"]
    Copies[("作業コピー / 新規出力先")]
    Runtime --> World
    Runtime --> Player
    Runtime --> Container
    Runtime -->|"対応する保存操作のみ"| Journal
    Journal -->|"保護対象ファイル"| World
    Journal -->|"保護対象ファイル"| Container
    Replay --> Journal
    World -->|"独立した移行処理"| Export
    Export --> Copies
```

- `journal.rs` はファイル数とサイズを制限し、対象拡張子も限定してredoログを検証・再生します。**無関係な保存ファイルすべてを横断して整合させる仕組みではありません。**
- `anvil_export.rs` / `anvil_import.rs` / `legacy_*` は本家形式向けの変換・解析を段階的に進めるためのものです。ライブAnvil常時保存の完成を意味しません。
- 元のMinecraft 1.7.10 / Forgeワールドは**直接書き換えず、バックアップ後の作業コピーで検証**します。
- 異常終了・復元失敗・複数ファイル境界のリスクは、対応機能と受け入れ試験を分けて記録します。

## 6. 変更から検証まで

```mermaid
flowchart LR
    Change["変更・Pull Request"] --> Fmt["cargo fmt<br/>書式確認"]
    Fmt --> Test["cargo test<br/>workspace / 全ターゲット"]
    Test --> Lint["cargo clippy<br/>警告をエラー扱い"]
    Lint --> Build["Releaseビルド"]
    Build --> Review["レビュー・PR統合判断"]
    Review --> LiveTest["無改造1.7.10クライアント実機試験<br/>必要な機能は別途実施"]
```

`.github/workflows/ci.yml` のRust CIはfmt・test・clippy・release buildを実行します。**CIのTCPテスト合格は、実クライアントを操作した受け入れ試験の代わりにはなりません。** 配布用バイナリや再現ビルド検証は別ワークフロー・別要件です。
