対象: Minecraft Java 1.7.10 / Protocol 5。Rustテストと無改造Java GUI実機受入を区別する。変更は必ずレビュー/CIを経由する。

## 起動・診断

- `cargo run -p vanilla-server -- --check-config` は `server.properties` を検査し、ネットワークを開かない。オフラインモードはループバックのみを許容。
- `cargo run -p vanilla-server -- --verify-world ./world` は `level.dat` か `flat.irw` を判定し読み取りのみ行う。作業中のトランザクションがあれば失敗し、勝手に復旧しない。
- `server.properties` の `level-type=DEFAULT` と `level-seed=文字列またはlong` を組み合わせると、新規IRW3バイオームワールドのシードに適用。既存ワールドと一致しない場合は起動拒否。`FLAT` と非空シードの組合せも意図しない非フラット生成を防ぐため拒否。
- `/stop` はOSコンソールのみ。接続中のプレイヤーを切断して保存した後、tick処理を止める。オンライン接続・資格認証は未対応。
- `cargo run -p vanilla-server -- --world ./world/flat.irw --backup-rotate ./backups 5` は**オフライン専用**。稼働中は`session.lock`が取得できず失敗する。管理者は停止後の定期メンテナンスとしてcron/タスクスケジューラから呼び出す。公開運用の定期ホットバックアップを保証しない。

## J96 データ移行の境界

本家形式の移行前に `cargo run -p vanilla-server -- --prepare-anvil-copy ./original-world ./migration-working-copy` を実行できる。既存の `level_dat.rs` / `legacy_world_inspect.rs` で元ワールドを検証した後、別名の新規ディレクトリに再帰コピーし、バイト一致とAnvil構造の再検査を行う。変換先が既存の場合は拒否する。元ワールドへの `session.lock` 作成も行わない。これは**元データを壊さない移行作業コピーの準備**であり、IRWへの互換変換を完了させるものではない。既存の `anvil_import.rs` / `anvil_export.rs` も従来どおり限定変換専用とする。未知のTileEntityやMod NBTの無損失移行を宣言しない。実運用ワールドはまず管理者が手動で複製し、複製先で読み取り専用検査→限定的変換→再検査、という手順を踏む。変換できない要素が1件でもあれば本番への置換は禁止。

## J97 クライアント実機試験

`docs/group-e/2026-10-21-E42-vanilla-client-e2e.md` の42-01〜42-09を統合受入基準とする。公式クライアントや資格情報はGitへ保存しない。人間によるGUI受入証跡が得られるまではBLOCKED/NOT_RUNとする。

## J99/J100

`workflow_dispatch` または `v*` タグで `.github/workflows/release.yml` がWindows/Linux用にビルドし、`BUILD-MANIFEST.txt`、`Cargo.lock`、`SHA256SUMS` を同梱する。SHA256は同じジョブ内で照合する。これは出自検査であり、完全なbit-reproducibleビルドの証明ではない。CIの品質ゲートは別途 `ci.yml` による。

## J92 運用専用スーパーバイザー（明示的なオプトイン）

`tools/maintenance_supervisor.py` はPython 3.9+標準ライブラリで動き、**自分で起動した子サーバー**だけを管理する。1時間以上の間隔を指定し、時刻到達時にOSコンソールへ `/stop` → 子プロセスの正常終了を待つ → `--verify-world` → `--backup-rotate` → 新しいサーバーを起動する。検証失敗・停止タイムアウト・バックアップ失敗時は**再起動しない**。ライブコピーは行わず、作業コピー・本家Minecraftサーバーに干渉しない。

Windows PowerShellの例（端末を開いたまま実行、必要ならタスクスケジューラでこのコマンドを起動）:

```powershell
python tools/maintenance_supervisor.py --server .\target\release\vanilla-server.exe --world .\world\flat.irw --backups .\backups --keep 7 --every-hours 24 -- --survival --whitelist .\whitelist.json
```

Linuxの例（運用者がsystemdユーザーサービス等へ登録できる。毎回起動させる周期タイマーと重複実行しないこと）:

```bash
python3 tools/maintenance_supervisor.py --server ./target/release/vanilla-server --world ./world/flat.irw --backups ./backups --keep 7 --every-hours 24 -- --survival --whitelist ./whitelist.json
```

- **自動保存のためプレイヤーを定期的に切断する**。実サーバーへ適用する前にメンテナンス告知とセーブ復旧演習を実施。
- シグナル/CTRL+Cでは通常停止のみでバックアップしない。OSコンソールから手動 `/stop` したときは監督スクリプトも終了する。
- 停止中のCLI単発 `--backup-rotate` も従来どおり使用可能。別プロセスのサーバーが稼働している場合はsession.lockで拒否する。
- サーバーの `/stop` がタイムアウトした場合、対象プロセスを強制終了して危険なバックアップを作らない。運用者が調査してから再開する。
- テスト: `python3 -m unittest discover -s tools -p 'test_*.py'`。これは実Minecraft GUI試験の代わりにならない。

## J98 Coverage-guided fuzz（手動/専用Runner）

`fuzz/` は主ワークスペースから分離したcargo-fuzzプロジェクト。実装済みのProduction Parserをそのまま呼ぶ2つのターゲット（Protocol5フレーミング、Anvil 1.7.10 NBT）を備える。入力の最大長は本番の上限値と合わせて制限する。

```bash
rustup toolchain install nightly
cargo +nightly install cargo-fuzz
cd fuzz
cargo +nightly fuzz run protocol5_frames -- -max_len=65536 -max_total_time=600
cargo +nightly fuzz run anvil_nbt -- -max_len=65536 -max_total_time=600
```

これは実行例であり、**このPRでは10分のfuzz実行やメモリ負荷評価を実施したものではない**。クラッシュケースは秘密情報を取り除いてから回帰テストへ取り込む。一般のCIでは既存J98決定論的smokeテストのみ自動実行。

## J100 依存と配布の追跡

リポジトリ直下 `Cargo.lock` をソース管理対象に加え、`rust-toolchain.toml` のRust 1.99.1と、CI/Releaseの `--locked` を一致させた。リリースジョブで依存解決を再実施してロックファイルを変更することは禁止。SHA256SUMSとBUILD-MANIFESTにOS・CPU・コミット・lockfileハッシュ・ビルド環境を収録する。

**これは監査可能なビルド出自の確保であり、Windows/Linuxの別マシンでのバイナリのバイト一致を保証するものではない**。配布前に両OSのワークフローを実行して起動し、独立した再ビルドと再現性差異を比較する必要がある。

## 2026-10-22 追加：J92 復元ドリル

世代別バックアップは元ワールドに戻さず、一時ディレクトリに複製して検査する。スクリプトは管理者による**明示的な実行のみ**（バックアップ世代フォルダーを選んで指定）で動作する。所有マーカー、通常ファイルのみか、ファイル総数・容量の上限、コピー前後の全ファイルSHA256、Rustサーバーの `--verify-world` をチェックする。コピー元が変化すればFAILとする。元ワールド、バックアップは変更しない。

```bash
python3 tools/verify_backup_restore.py --server ./target/release/vanilla-server --backup ./backups/backup-123456-1234
python3 -m unittest discover -s tools -p 'test_*.py'
```

Windowsなら `--server .\\target\\release\\vanilla-server.exe` を使用。上記のバックアップ名は例なので、実際に `--backup-rotate` で作成された保存世代を指定する。元のバックアップ容量と同等の一時領域が必要。**整合性チェックと復旧コピーのバイト一致**は検査できるが、復元先をオンライン稼働させたときの正常性、実クライアント描画やGUI、任意のModデータ互換は保証しない。

## 2026-10-22 追加：J98/J99/J100 専用検証の運用

- `.github/workflows/fuzz.yml`: GitHub Actionsで手動実行する、Protocol 5とNBTのcoverage-guided fuzz。各ターゲット180秒、最大入力64KiB、RSSリミット1024MiB。通常のpush/PRごとの実行は避け、CI容量の無駄な消費を抑える。実行成功は長期安全性を証明しない。
- `.github/workflows/release.yml`: Windows/Linuxの各runnerでビルドした**そのバイナリ**を `--help` で起動・終了させ、使用方法の表示をsmoke確認してから配布物にまとめる。これを実クライアント接続試験の代用にはしない。
- `.github/workflows/reproducibility.yml`: 手動実行し、同じコミットとlockfileを**別々のCargo targetディレクトリ**でリリースビルドして、両バイナリをバイト一致比較。結果はGitHub Actions SummaryへSHA256とPASS/MISMATCHを記録し、差異があれば失敗する。異なるホストや異なるOS間の同一ハッシュは想定せず、各OS内で比較する。
- 上のワークフローは追加しただけでは実行結果がない。GitHubで実行が確認できるまでは `NOT_RUN` とする。J97（無改造Java 1.7.10の操作付きGUI受入）は引き続き別試験として必須。
