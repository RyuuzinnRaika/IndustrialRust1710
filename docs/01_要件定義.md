# 要件定義書 v0.2 — IndustrialRust1710

- 作成：2026-10-19
- 状態：要件定義（未検証項目を明示）
- 対応対象：Minecraft Java Edition **1.7.10**、Forge **10.13.4.1614**基準、Minecraftプロトコル **5**
- 目的：既存の1.7.10工業化Modを活用し、Rustネイティブ計算／段階的なJavaバイトコード変換／互換ランタイムの研究によって、実測に基づく高速化を達成する。

## 0. 想定利用者と用語

サーバー管理者は、既存の1.7.10 Modpackのクライアントを維持して大規模工業化ワールドを運用したい。対象Modpack・Mod名はまだ選択されていない。まず汎用のForge 1.7.10基準環境を整え、テスト用Modから段階的に検証する。

- 「JARをロード」：実行環境にMod JARを認識させること。処理の正しさまでは含まない。
- 「互換実行」：実際の機械機能、通信、アイテム保存、ブロック配置が元環境と一致すること。
- 「Rustへコンパイル」：Javaクラス／バイトコード中の**サポート済み部分**をネイティブ処理へ変換し、互換ランタイム／アダプターを通して実行すること。
- 「無変更Mod対応」：配布されたJARにパッチや変換前処理を要求せず、Forgeベースラインと同等に実行すること。初期はLegacy-JVMモードのみで成立を検証する。

## 1. 対象と非対象

### 対象
- Minecraft Java 1.7.10のサーバー側機能、ForgeのロードおよびFML互換経路。
- 既存Java製工業化Modの読み取り・分類・依存解決・互換動作の検証。
- 工業ネットワーク／機械演算のRust高速化、負荷計測、データ保護。
- サーバーを中心としたLinux/Windows上の起動・診断・デプロイ。

### 初期対象外
- Javaクライアント側ModのRust化、Minecraft 1.8以降、NeoForge/Fabric互換、Bedrock互換。
- 既存のすべてのForge 1.7.10 Mod JARを無改変でRustネイティブ実行できるという保証。
- 未許諾のMod、Minecraft資産、改変された配布物の再配布。

## 5. 実行モード / 成果の扱い

| モード | JAR | 世界状態の所有者 | 想定用途 | 現在 |
|---|---|---|---|---|
| A: Legacy-JVM | Forgeがそのまま実行 | Forge/JVM | ベースラインと互換維持 | 未統合 |
| B: Hybrid-Offload | Forge実行＋選択した関数をRustへ移管 | Forge/JVM | 性能改善の本命 | 未実装 |
| C: Rust-Native | 対応Mod機能のみRust実行 | Rustサーバー | 長期的な1.7.10互換 | 未実装 |

JARを読めることは互換実行でも、Rustへの変換成功でもない。モードAはRust製ゲームサーバーではなく、目標へ至る検証・移行手段である。

## 6. 完了判定

- **MVP（Stage A）**：Forge 1.7.10の既存Modでの実行ベースライン、Mod/JAR解析レポート、Rust工業計算テスト、同条件の性能データが揃う。
- **実用版（Stage B）**：少なくとも選定した工業化Modの1機能でRust offloadの結果一致、速度改善、セーブ安全性を証明。
- **長期成果（Stage C）**：対応範囲を明示したRustネイティブの1.7.10ゲームサーバーにModdedクライアントが接続・操作できる。全Mod互換は独立した追加目標。

## 7. 未確定の判断（開発を止めない）

- 対象Mod／Modpack：「その他」で個別名称未指定。まず再配布可能なテストModで着手。
- Java実行環境：通常Forge 1.7.10はJava 8ベース。GTNH等の独自更新系は専用サーバーパッケージ／Java 17–21が必要な場合があるため別マトリクス管理。
- Rustサーバーの下地：Pumpkinは現行版対応中心であり、1.7.10対応済みではない。移植コストと独立実装を先に比較する。
- 目標性能：工場規模・CPUを定義した測定シナリオで確定し、数字だけを先に保証しない。

## v0.4 開発スコープの変更（2026-10-19、ユーザー指定）

**Modの追加・削除やConfig変更は頻繁に起こるため、Mod互換の実装は一時停止する。Rust製Minecraftサーバーの基本機能を先行する。**

現段階の実装優先順位:
1. P0: Java Edition 1.7.10 / Protocol 5でバニラクライアントの接続、Login、Play、切断を完成させる。
2. P0: Tick駆動、ワールド生成・チャンク/ブロック状態管理、移動・相互作用、破壊と設置の検証。
3. P0: NBT/Anvilの作業コピーを使った読み書き、異常終了と再起動の復旧検証。
4. P1: 複数プレイヤー、チャット/コマンド、権限/オンライン認証、公開用セキュリティの導入。
5. P1: バニラのインベントリ/クラフト/サバイバル/Mob/AI/光源/レッドストーン/物理の段階実装。
6. **保留: Forge/FML、Mod依存解決、Mod ID同期、CoreMod、Java→Rust変換、Mod/Config操作。** 既存の読み取り専用mod-analyzerは保管・維持するだけで新しいMod実行機構には着手しない。

現行vanilla-serverは1人向けCreative固定ワールドのプロトタイプ。オンライン認証はなく、世界保存は独自IRW1形式でありNBT/Anvil互換ではない。実機1.7.10クライアント検証前に「バニラサーバー完成」と表示してはならない。


## v0.5 参加制御とバニラ基本動作（2026-10-19）

- AUTH-V01 P0: ホワイトリストによる参加者名の許可判定（初期は拒否、設定ファイル欠落/破損で拒否）。
- AUTH-V02 P0: ホワイトリストはログインごとに再読み込み、参加中の取消は定期チェック。
- AUTH-V03 P0: ユーザー名ホワイトリストは本人確認ではない。オンライン認証機能がない間はローカルバインドを既定値とし、LANは危険性を理解した明示許可が必要、WAN公開禁止。
- VAN-V01 P0: 20Hz monotonic Tickスケジューラ。Tick時間・処理時間・20TPS維持率を今後計測しながら本体を実装。
- VAN-V02 P0: プレイヤー・ワールド・複数チャンクの状態管理、保存とクラッシュ復帰。
- VAN-V03 P0: 通常のバニラゲームに必要な Survival/Inventory/Crafting/Mob/物理/光源/レッドストーンまで段階的に実装する。Modは保留。
- VAN-V04 P0: 「普通に遊べる」受け入れ試験は、バニラ1.7.10実機クライアントで複数プレイヤー、基本サバイバル、セーブ復帰、数時間耐久を含む。通信PoCのみを完成判定に使わない。


## v0.6 複数プレイヤー基盤（2026-10-19）

- VAN-MP01: 同時入場は最大8人、重複名は禁止。各プレイヤーに一意なセッション内Entity IDを割り当てる。
- VAN-MP02: Minecraft 1.7.10 Protocol 5のPlayer List 0x38（1.8以降とは異なる）、Spawn Player 0x0C、Teleport 0x18、Destroy 0x13で相互同期する。
- VAN-MP03: チャットとサーバー権威側のブロック更新を全プレイヤーへ送信。送信を有界キューに隔離して低速端末がサーバー全体を止めない。
- VAN-MP04: 退出・タイムアウト・ホワイトリスト取消でEntityとタブ一覧を解除。最大8人のプレイヤーデータを個別保存。
- VAN-MP05: 少なくとも2接続の実TCPテストでログイン、同名拒否、移動、ブロック、チャット、退出を確認。Vanilla 1.7.10 GUIによる最終動作確認は別途必要。
- 著作権: Pumpkinコードのコピーを禁止し、Protocol 5公開データ仕様から独自にRustで構成する。
