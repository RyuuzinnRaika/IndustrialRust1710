- **安全上の制限**: チェストとカーソルの異なる種類のアイテム交換、チェストとホットバーの数字キー交換、2連チェスト、アイテム入りチェストの破壊は禁止。チェストとプレイヤーの保存先は別ファイルなので、異常終了時の**アイテム消失リスクは残る**（複製防止のため出所を先に保存）。チェストのAnvil TileEntityへの書き出し・インポートは未対応です。
- チェストはGUIと保存が対象。かまど/ホッパー/チェストの物理・赤石・ブロックエンティティ更新は未対応。これだけでは通常のバニラSurvival完成とはみなしません。

## 2026-10-20: クラフト機能（限定実装）

- プレイヤーの2×2クラフト入力（Window 0、1〜4）と作業台の3×3（専用ウィンドウ1〜9）をサーバーが保持します。
- 初期サバイバル向けレシピ：原木→木材、木材→棒、作業台、チェスト、かまど、木/石の剣・ツルハシ・シャベル・斧・クワ。
- 完成品スロット（0）はレシピから毎回計算し、取得時に**入力を1個ずつ消費**します。クライアントの「完成品を持っている」という申告は採用しません。
- 作業台（ブロックID 58）の設置と右クリックでProtocol 5のGUIが開きます。Crafting Tableウィンドウ（0x2D）、Window Items（0x30）、Confirm Transaction（0x32）に対応。
- クラフト中の素材は別セーブではなく、サーバーが管理する従来のプレイヤーインベントリJSONに保存します。作業台を閉じても素材はこの試験版では**保持**され、再入場後に再利用できます（バニラと挙動が異なります）。
- **未対応**: すべてのレシピ/道具耐久・NBT・防具・クラフト結果の連続Shift大量生産（現状は1回ずつ）・ドラッグ操作・材料が容器を返すレシピ、チェスト/かまどの実機能とGUI、重力/Mob/戦闘/地形生成/Anvil完全対応。
- バニラ1.7.10クライアントの実機GUI確認は別途必要です。Rust製ソケット試験と実機は区別します。

## 2026-10-20: Protocol 5 プレイヤーインベントリ操作（限定実装）

Window 0 の通常クリック・右クリック・Shiftクリック・数字キーでのホットバー入れ替えに対応しました。アイテム移動・スタック分割・最大64個までの統合を**サーバー所有のインベントリ**から計算し、クライアントが偽装したClicked Itemではアイテムを追加しません。操作ごとに保存した上で Confirm Transaction (0x32) とWindow Items (0x30)、カーソルSet Slot (0x2F)を返します。カーソル内のアイテムも保存・再ログインで復元します。

**未対応**: 2×2/3×3クラフト、結果スロット、防具、ドラッグ配置、外への投げ捨て、チェストなどの追加ウィンドウ、NBT装備、クラフトレシピ、通常のサバイバル全機能。非対応操作は受け付けず、状態を再同期します。実Minecraft GUIでの操作確認は未実施です。

# Minecraft 1.7.10 Rustバニラ最小サーバー（開発版）

## 目的

Mod JAR/Forge/FML/Configは扱わず、バニラ1.7.10（Protocol 5）用のRustネイティブサーバーを単独で動かす。

## 起動

~~~bash
cp config/whitelist.example.json whitelist.json
# whitelist.json に許可するプレイヤー名を指定してから起動
cargo run --release -p vanilla-server -- --bind 127.0.0.1:25565 --world ./world/flat.irw --whitelist ./whitelist.json
~~~

初期待受は127.0.0.1のみ。**ホワイトリストファイルがなければ起動拒否し、空リストは全員拒否**。LAN実験に限り --bind 0.0.0.0:25565 --insecure-offline-lan を**明示的に**指定できるが、**Microsoft/Mojangのユーザー認証なしのoffline-modeであり、許可済みプレイヤー名の偽装が可能**。インターネット公開してはいけない。最大8人まで。Minecraftの実ワールド保存先を指定しないこと。

## 今回の対応範囲

- Handshake、Status/Ping、Login Start、名前検査、offline UUID、Login Success。
- Play: Join Game、Creative、Spawn、Health、Player Abilities、Time、Position/Look。
- 現在地を中心とした5×5チャンク（最大25列）の逐次配信、視界外チャンクの解放、および1.7.10のzlib圧縮Chunk Data。座標は±16384ブロックの安全な範囲内に制限。
- 20Hzの単調Tick時計と定期時刻通知（本格的なゲーム処理Tickではない）。
- ホワイトリストによる名前照合（JSONは毎ログインで読み直し、接続中も約2秒ごとに再照合）。
- 最大8人の同時ログイン（同名接続禁止）、1.7.10 Player Info/Named Entity Spawn/Teleport/Destroy、双方向プレイヤー表示・移動同期。
- 移動パケット、KeepAlive、共有チャット、/help、/save、/list。
- Creativeでの限定的な通常ブロックの設置・破壊、全接続プレイヤーへの更新送信、距離・座標検証。
- プレイヤーのWindow 0（45スロット）の初期同期`0x30`、ホットバー選択`0x09`、Creative Inventory Action`0x10`、Slot更新`0x2F`。スロット36〜44の選択中アイテムに一致するブロックのみ設置を許可。偽装されたBlock PlacementのheldItemではブロックを生成しない。
- インベントリは独立の`players/<name>.inventory.json`へ上限16KiBで保存し、再接続時に復元。形式不正・破損ならログインを拒否。アイテムNBT付きはまだ非対応。
- 変更ブロックの独自IRW1セーブ形式（サイズ制限、簡易破損検出、保存失敗時ロールバック）。
- プレイヤー座標をplayers/<小文字名>.datのgzip NBT形式に保存し、再接続時の位置を復元。旧バージョンのplayers/<小文字名>.jsonは新しいNBTが存在しない場合のみ読み取り、次回保存時にNBTへ移行。約5秒ごとと正常・異常切断時に記録。ファイル破損時はログイン前に拒否して管理者に修復を促す。
- 世界の安全上限（x,zが-16384以上+16384未満）を超える移動パケットは、サーバー権威側の位置へ戻す。

## 未対応

- Mod/Forge/FML、20TPS上の正式なブロック/エンティティ更新、Mob/AI、サバイバル、完全なインベントリ操作/クラフト、物理・光源更新、レッドストーン。マルチのMinecraft GUI実機動作・アクセス公平性・長距離負荷試験は未検証。
- MIT OR Apache-2.0ライセンスのfastnbt依存を使用したgzip NBTプレイヤー保存は追加済み。ただしAnvilの独立スナップショット**書き出し**は実装。サーバーが生成したAnvilスナップショットから新規IRW1への限定的な読み戻しは追加済み。一般的なMinecraftワールドの読み込み・既存Minecraftワールドとの完全互換・本番ワールドへの自動移行は未実装。
- 公開用のオンライン認証/セキュリティ/権限管理。実機Minecraft GUI接続は別途確認が必要。

TCPの断片化に対応するためPlayステートの受信は`BufferedFrameReader`が未完フレームを保持します。50msの読み取りタイムアウトをまたぐVarInt/本文の受信もテストします。ネットワーク遅延がある場合、1回のreadが完整パケットであると仮定してはいけません。

現段階の完成判定はRust単体テストと独立したProtocol 5ソケットテストが通ること。Playパケットを送れる状態と「完全にMinecraftを遊べる」は別。

## マルチプレイヤーの限界

プレイヤー一覧・生成・移動・退出、チャット、ブロックの同期をProtocol 5で行います。同一ユーザー名の2重ログインは拒否。初期設定はlocalhostで、LAN接続には明示的な不安全フラグが必要です。**ホワイトリストの名前照合は本人確認ではないため、名前を偽装できる環境で公開しないでください。** ネットワーク送信用に最大512イベントの有界キューを使用し、低速クライアントではイベントを捨てる可能性があります。完全なインベントリ・サバイバル・アンチチート・動的チャンク生成は未実装です。

## 動的チャンクの既知の制限

- クライアントへは現在地中心の半径2チャンク（合計最大25列）を送信。境界を越えた際に差分のみを送信・解放する。負の座標も床関数とEuclidean除算で扱う。
- 平坦地形は計算で生成し、変更されたブロックのみ独自IRW1ファイルへ保存（最大65,536変更）。**Anvil .mcaファイルには未対応**。サーバーのバックアップを取得してから実行する。
- デフォルト地表以外の高さに編集があるチャンクは、必要な垂直セクションを追加した形式で送信する。すでに配信済みのチャンクへ新規垂直セクションが生まれた場合の見た目の同期は実機追加検証が必要。
- 現在は機能検証用で、チャンク生成の非同期化、スレッドプール、LRU、tickごとの負荷制御、地形生成アルゴリズムなどは未実装。

## Anvil 1.7.10形式スナップショット出力

```bash
cargo run --release -p vanilla-server -- --world ./world/flat.irw --export-anvil ./exported-world
```

- 元の`IRW1`を読み込み、`./exported-world/region/r.X.Z.mca`と`level.dat`を別の新規ディレクトリーへ生成する。`--export-anvil`時はサーバーの待受を開始しない。
- 出力ディレクトリーが既存の場合、生成前に失敗。最大256チャンク列をスナップショット化。初期5×5列と編集がある列を含む。
- チャンクは1.7.10以前のNBT`Sections/Y/Blocks/Data/BlockLight/SkyLight`、`Biomes`、`HeightMap`などを出力。ライティングやレッドストーン・エンティティは簡易/空実装であり、既存ワールドへの追加やGUI動作は**未検証**。
- 出力はサードパーティMIT系の`fastanvil`とMIT/Apache-2.0の`fastnbt`を依存として利用し、Pumpkin由来ソースはコピーしない。
- バックアップなしでMinecraft実ワールドに上書きしない。編集済み`IRW1`のバックアップを保管する。


## Anvilスナップショットの安全な読み戻し

```bash
cargo run --release -p vanilla-server -- --import-anvil ./exported-world --world ./world/restored.irw
```

- 現在は**IndustrialRust1710自身の`--export-anvil`で作成したフラットワールドだけ**を入力対象とする。入力先`level.dat`の識別情報を検査する。一般的なVanilla/Forgeワールドを取り込めるわけではない。
- インポートは**オフライン専用**でTCP待受は開始しない。すべてのファイルを読み終わり検証した後、`IRW1`を新規作成する。すでに保存先が存在していれば失敗し、勝手に上書きしない。
- NBTは展開サイズ制限付きで読み込み、リージョンセクター配置/重複、ワールド境界、チャンク座標、セクションサイズ/重複、最大256チャンク、編集の最大65,536件を検査する。
- インポートではMob、TileEntity、TileTicks、高ID追加セクション、未対応ブロックに対応していないため**拒否**する。取りこぼして保存することを避けるための制約。
- 出力元の`IRW1`と復元したファイルのバイト一致テストをCIで行う。ゲーム本体の正規保存形式は依然として`IRW1`。`Anvil (.mca)`をサーバー内で直接読み書きする機能は未実装。
- `save_new`は同一ディレクトリーのステージングファイルとhard linkによる公開を利用する。中断で`.importing`が残る場合、手動調査・削除が必要。hard linkをサポートしないファイルシステムではエラーとなる。

## Creativeインベントリの現在の制約

Creativeユーザーの45スロットのうち通常インベントリ/ホットバー9〜44のみを同期・保存できる。防具・クラフト欄、通常のWindow Clickによるドラッグ、チェスト・かまどなどの他ウィンドウ、アイテムドロップとエンティティ、アイテムNBTは未実装。Click Windowは確定処理しないため、拒否トランザクションとWindow Items同期でクライアントの内容を戻す。これはSurvival InventoryやCraftingの完成ではない。

Minecraft 1.7.10 / Protocol 5の`C09 Held Item Change`、`C10 Creative Inventory Action`、`S30 Window Items`、`S2F Set Slot`形式を使用。過去の「クライアント申告のheldItemを無条件に採用」する挙動は廃止。


## オプトインSurvivalの第一段階

`--survival`を指定した起動では、Join Gameのゲームモード0と飛行能力なしを通知し、Creative Inventory Actionを拒否する。ブロック破壊ではProtocol 5 `C07`の0（開始）・1（中断）・2（終了）を区別する。開始座標・ブロックID・経過時間・8ブロック以内の距離を検査し、対応する草・土・石等から1個だけ収穫物を選択プレイヤーのインベントリに直接追加する。容量不足なら採掘を確定しない。

Survivalモードでは、`C08`の設置時にサーバーが記録した所持アイテムと一致する場合のみブロックを配置し、個数を1減らす。設置消費は世界編集に先立ってディスクへ書き込む（クラッシュ時に消費だけが発生する可能性は残るが、アイテムの複製リスクを抑制）。`players/<username>.survival.inventory.json`に保存し、Creativeの同名プレイヤーの在庫と分離する。

**未対応**：本来のバニラ採掘硬度・ツール速度、Drop Entity/アイテム拾得、Click Window/クラフト/チェスト、Mob、空腹/体力減少、死亡、ネザー/エンド、重力/落下、光源/液体/レッドストーン。フラットワールドとオフライン名簿認証の制約は変わらない。


## Protocol 5の地面アイテム（Rust、限定実装）

`0x0E` Spawn Object(type=2)でアイテムEntityを生成し、`0x1C` Entity Metadataのindex 10/type 5（Slot）に実際のStackを設定。サーバーはそれらをPlayerHubのイベントで配信する。近くにいるプレイヤーの在庫に空きがあり、拾得遅延後は `0x0D` Collect Item → `0x13` Destroy Entities → `0x2F` Set Slot により同期する。

地面アイテムはIRW1と別の上限128KiB・最大512件の`world/<filename>.drops.json`に保存。破損時は起動を拒否する。遅延/所持上限/二重取得防止はサーバー側で管理。既存Worldの編集が成功してからアイテム状態へ記録するため、書き込み障害で消失する可能性がある。拾得ではGroundItems状態の削除・永続化を先に確定してから、所持品ファイルに加算する。**これらは完全な複数ファイルトランザクションではない**ため、重大なI/O障害やクラッシュでアイテムが失われる可能性がある。

今後の対象: item实体の重力/衝突、落下時位置、消滅時間/統合、Qキー投げ、拾得範囲とチャンク追跡、チェスト・クラフトとアイテム表示。実GUIクライアントによる描画・操作は未検証。
